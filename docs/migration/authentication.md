# Password, OIDC authentication and sessions (.NET)

MAZ-53 ports password registration, login, `me` and logout from the legacy Node server (`server/application/auth.ts`, `server/http/auth.ts`, `server/http/middleware.ts`) to `apps/backend`. MAZ-54 adds OIDC sign-in (`/api/auth/oidc*`, see [OpenID Connect](#openid-connect-maz-54)). The legacy server keeps running unchanged; `contracts/openapi.json` still marks these operations `legacy` because Node implements them until cutover (MAZ-63/65).

**Imported password accounts must reset their password.** The legacy scrypt hashes are not verified: the backend uses a maintained library format instead of custom cryptography. Imported **sessions** stay valid until their original expiry (at most 30 days), so signed-in devices keep working during that window. Imported rows are not rewritten; a legacy hash simply never verifies, and login returns the usual generic `401`. **There is no password reset flow yet** (neither server has one). Until one exists, affected users cannot sign in with a password once their imported sessions expire.

## Compatibility

| Area | Behavior (same as legacy unless noted) |
| --- | --- |
| Password hash | **Difference from legacy.** New and upgraded hashes use ASP.NET Core Identity `PasswordHasher` v3 (PBKDF2-HMAC-SHA512, 100,000 iterations, 128-bit salt embedded in the hash, base64), stored in `users.password`. `users.salt` is left empty for new accounts. Legacy scrypt hex hashes (Node `crypto.scrypt`) are **not** supported. |
| Hash verification | Identity compares hashes in constant time. Missing users, empty OIDC-only passwords and legacy scrypt hashes are checked against a dummy hash, so they cost the same as a wrong password and all return the same `401`. When Identity reports that a hash uses outdated parameters, a successful login rewrites it, but only if the stored hash has not changed in the meantime. |
| Email | Trimmed with JavaScript's whitespace set, ASCII-lowercased (plus U+212A → `k`), checked against zod 4's email pattern and limited to 254 UTF-16 units. Lookup and uniqueness are bytewise (`C` collation), as in SQLite. Legacy rows stored with uppercase letters stay unreachable by password login, exactly as before; they are not rewritten. |
| Password | 10–256 UTF-16 code units, not trimmed. |
| Register | Rate limit → JSON parse → policy (`403 Account registration is disabled on this server.`) → validation (`400 Enter a valid email and a password of 10–256 characters.`) → duplicate check (`409`). The user, ledger (revision 0, CAD) and the 12 default categories are inserted in one transaction. A concurrent registration for the same email waits on the unique index and gets the same `409`. Any other failure rolls back all rows and returns the generic 500. |
| Login | Invalid input, unknown email and wrong password all return `401 Email or password is incorrect.` |
| Tokens | 32 random bytes as lowercase hex (64 characters). Only SHA-256(token text) is stored in `sessions.token_hash`. |
| Lifetime | 30 days from issue, with no sliding renewal. Valid while `expires_at > now`; time is truncated to whole milliseconds, so the boundary matches the legacy integer expiry. Issuing a session first deletes sessions with `expires_at < now`; their push devices are removed by the database cascade. |
| Transport | Register/login return `{token,email}` and set `penny_session=<token>; HttpOnly; SameSite=Lax; Path=/api; Max-Age=2592000` (plus `Expires`), with `Secure` when configured. Logout deletes only the current session, expires the cookie and returns `{ok:true}`. ASP.NET writes cookie attribute names in lowercase; browsers treat them case-insensitively. |
| Precedence | A well-formed `Authorization: Bearer <64 lowercase hex>` header always wins, even when the token is unknown or expired. A malformed header falls back to the first `penny_session` cookie. |
| Protection | Every endpoint, and every unknown route, requires a session unless it is marked `[AllowAnonymous]` (health, info, ready, register, login and development docs). Anonymous requests get `401 Please sign in to continue.`; authenticated requests to unknown routes get `404 API route not found.` Public routes never read session storage, so liveness does not depend on PostgreSQL. |
| Origin/CSRF | Any non-GET request whose `Origin` header is not in the allowed list gets `403 This origin is not allowed.` This includes preflights. Requests without an Origin header, such as native clients, are not checked. |
| CORS | Allowed origins are reflected with `Access-Control-Allow-Credentials: true`. Preflight allows GET/HEAD/PUT/PATCH/POST/DELETE and any request header. |
| Rate limit | Register, login, OIDC start and OIDC complete share one fixed 15-minute window of 40 requests per client in each process. IPv6 clients are grouped by /56, and IPv4-mapped addresses count as IPv4. A blocked request gets `429 Too many attempts. Please try again in 15 minutes.` with `Retry-After`. **Difference:** the draft-8 `RateLimit`/`RateLimit-Policy` headers are not sent. Counters are in memory and are lost on restart, as before. |

## Configuration

| Setting | Legacy variable | Default / behavior |
| --- | --- | --- |
| `Auth__AllowRegistration` | `ALLOW_REGISTRATION` | `true`. Must be `true` or `false`. |
| `Auth__SecureCookies` | `COOKIE_SECURE` | `false`. Set `true` whenever clients reach the API over HTTPS. |
| `Auth__AllowedOrigins` | `CORS_ORIGINS` | `http://localhost:8081,http://localhost:3001`. A comma-separated list of exact browser origins (`scheme://host[:port]`). The host must be lowercase, with no path and no default port. Startup fails on any other form, so the CORS and origin checks cannot disagree. |
| `Auth__TrustedProxies` | (none) | Empty. A comma-separated list of IPs or CIDR ranges. |
| `Auth__RateLimitPermits` | (none) | `40` per 15 minutes; bounded 1–10,000. Tests use their own hosts. |

Invalid values fail before the server listens, naming the setting.

### Reverse proxies

Like the legacy server, the backend trusts **no** forwarding headers by default, not even from loopback. Behind a reverse proxy, every client then shares the proxy's rate-limit bucket. Set `Auth__TrustedProxies` to the proxy's address, for example `Auth__TrustedProxies=10.0.0.2` or `172.18.0.0/16`. `X-Forwarded-For` is then honored for one hop from those addresses only. Never list networks that untrusted clients can connect from, because they could then pick their own rate-limit key. `X-Forwarded-Proto` is not used: cookie security is explicit through `Auth__SecureCookies`. The proxy must pass the browser's `Origin` header through unchanged.

## OpenID Connect (MAZ-54)

MAZ-54 ports `GET /api/auth/oidc`, `POST /api/auth/oidc/start` and `POST /api/auth/oidc/complete` from `server/application/oidc.ts`, `server/infrastructure/oidc.ts` and `loginOidc` in `server/application/auth.ts`, with the same status codes, messages and shapes. Clients need no change: they still start an attempt, open `authorizationUrl` in the system browser or a popup, and post the `transaction` they kept plus the full `callbackUrl` they received.

### Flow and checks

| Step | Behavior (same as legacy unless noted) |
| --- | --- |
| Availability | `GET` returns `{enabled:true,label}` when configured and `{enabled:false}` otherwise. Start and complete return `404 Single sign-on is not configured.` when OIDC is off, after the usual rate limit and JSON parsing. |
| Start | The `redirectUri` must equal one configured URI exactly, otherwise `400 This sign-in redirect is not configured on the server.` The server creates a 64-hex `transaction` (returned once, stored only as SHA-256), plus a random state, nonce and PKCE verifier (32 bytes each, hex). The authorization URL uses the discovered `authorization_endpoint` with `response_type=code`, `scope=openid email profile`, `state`, `nonce`, `code_challenge` and `code_challenge_method=S256`; the transaction, verifier and client secret never appear in it. `expiresAt` is Unix milliseconds, 10 minutes ahead. A discovery failure deletes the attempt and returns `400 The sign-in provider is unavailable. Please try again.` |
| Complete | The body needs a 64-lowercase-hex `transaction` and a `callbackUrl` of at most 8,192 characters (`400 Invalid sign-in response.`). The attempt is **consumed before** any provider call; a missing, already used or expired attempt is `401 Sign-in expired. Please try again.` Every later failure is `401 Sign-in could not be verified. Please try again and allow access to your verified email.` and the attempt stays consumed. |
| Callback | The part before `?` must equal the attempt's redirect URI byte for byte, with no fragment. `state` must match. Any `error` parameter (for example, the user cancelled) fails. A returned `iss` parameter must equal the issuer, and is required when discovery advertises `authorization_response_iss_parameter_supported` (RFC 9207). `state`, `code`, `iss` and `error` must not repeat. |
| Code exchange | Server to server, at the discovered `token_endpoint` (HTTPS only), with `code`, the exact `redirect_uri`, `code_verifier` and `client_id`. Confidential clients also send `client_secret` in the body (`client_secret_post`, as legacy); public clients send no secret. The response must be JSON with `access_token`, `id_token` and `token_type`. Provider tokens are never returned to clients or stored. |
| ID token | Validated by `Microsoft.IdentityModel` (`JsonWebTokenHandler` and `OpenIdConnectProtocolValidator`): RS256 signature with a key from the discovered JWKS, `iss` equal to `Oidc__Issuer`, `aud` containing `Oidc__ClientId` (and `azp` when present), `exp` (30-second clock tolerance) and required `iat`/`sub`, the attempt's nonce, and `at_hash` when present. An unknown key ID triggers a JWKS refresh. |
| Email | Taken from the ID token, or from UserInfo (HTTPS, JSON, `sub` must match) only when the ID token has no `email` claim. It must be a valid email (the zod rule, at most 254 characters, not trimmed), and `email_verified` must be JSON `true`. It is lowercased. |
| Account | The stable `(issuer, subject)` pair finds the account, so a changed provider email still signs in to the same account and the response shows the stored email. An unknown identity needs `Oidc__AllowRegistration=true` (`403 New single sign-on accounts are disabled on this server.`). An existing account with the same email is **never linked** (`409 An account already uses this email. Sign in with its existing method; automatic account linking is disabled.`). Otherwise the user (empty password, random salt), identity, ledger and default categories are inserted in one transaction. If a concurrent first sign-in for the same identity or email wins, the loser gets `409 This account already exists. Please try signing in again.` (or signs in if the identity is already committed when it looks); any other failure rolls back every row and returns the generic 500. |
| Session | The same 30-day `penny_session` cookie and `{token,email}` response as password login. |

### Pending attempts in PostgreSQL

**Difference from legacy.** The Node server kept attempts in process memory, so a restart lost in-flight sign-ins and only one instance could run. The .NET backend stores them in `penny.oidc_attempts` (migration `AddOidcAttempts`): primary key `transaction_hash` (SHA-256 of the transaction), the redirect URI, state, nonce, PKCE verifier and `expires_at`, with format checks and an index on `expires_at`.

- **Single use.** Completion reads the row and then deletes it by key; only the request whose delete affects the row continues. A concurrent redemption waits on the row lock and deletes nothing, so it gets `401` without contacting the provider.
- **Expiry.** An attempt is valid while `expires_at > now`, 10 minutes after start. Every start first deletes expired attempts.
- **Bound.** Like legacy, a start is refused with `403 Too many sign-in attempts. Try again later.` while 1,000 unexpired attempts exist. Concurrent starts may each see room, so this is a flood guard, not an exact quota.
- **Restarts and instances.** Attempts survive restarts and work across API instances on the same database. The provider discovery document and JWKS are cached per process and fetched again after a restart.
- **Secrets at rest.** State, nonce and verifier are stored in plain text for at most 10 minutes; without the transaction (only its hash is stored) and the provider's authorization code they cannot complete a sign-in. They are not imported: in-memory legacy attempts are lost at cutover, so users who are mid-sign-in start again. The importer does not read or check this table.
- `development/grant-runtime.sql` already grants the runtime role DML on new tables; re-run it after `migrate`, as for every migration.

### Configuration

| Setting | Legacy variable | Default / behavior |
| --- | --- | --- |
| `Oidc__Issuer` | `OIDC_ISSUER` | Unset (OIDC off). An HTTPS URL without credentials, query or fragment. It must equal the provider's advertised `issuer` **exactly** (including any trailing slash); discovery is read from `<issuer>/.well-known/openid-configuration`. |
| `Oidc__ClientId` | `OIDC_CLIENT_ID` | Unset. Setting either the issuer or the client ID turns OIDC on, and then the issuer, client ID and redirect URIs are all required. |
| `Oidc__ClientSecret` | `OIDC_CLIENT_SECRET` | Unset: a public client using PKCE only. Set it for a confidential client. Keep it in the secret manager; it is sent only to the token endpoint and is never logged or returned. |
| `Oidc__RedirectUris` | `OIDC_REDIRECT_URIS` | Comma-separated exact URIs: HTTPS, `http://localhost`/`http://127.0.0.1`, or `penny://auth/callback`, without query or fragment. Register each one with the provider. Typical: `https://penny.example.com/auth/callback,penny://auth/callback`. |
| `Oidc__Label` | `OIDC_LABEL` | `Single sign-on`. |
| `Oidc__AllowRegistration` | `OIDC_ALLOW_REGISTRATION` | `false`. Must be `true` or `false`. **Difference:** legacy treated any value other than `true` as `false`; a typo now fails startup. Independent of `Auth__AllowRegistration`. |

Empty values count as unset, as in legacy. Invalid settings fail before the server listens, naming the setting and never including the secret.

**Provider requirements.** OIDC discovery; Authorization Code with S256 PKCE; RS256-signed ID tokens (openid-client's default; other algorithms are refused, as before); the `openid email profile` scopes; a verified email in the ID token or a JSON UserInfo response (signed UserInfo responses are not supported); and `client_secret_post` for confidential clients. Provider endpoints must use HTTPS. Provider calls time out after 10 seconds, follow no redirects, accept at most 1 MiB and are excluded from HTTP client logging.

**Troubleshooting.** `400 The sign-in provider is unavailable` means discovery or JWKS could not be fetched, or the advertised issuer differs from `Oidc__Issuer`; compare it with the provider's `/.well-known/openid-configuration`. `400 This sign-in redirect is not configured` means the client's redirect URI is not in `Oidc__RedirectUris`. `401 Sign-in expired` means the attempt was older than 10 minutes, already used, or started against another database. `401 Sign-in could not be verified` covers cancellation at the provider, a redirect URI registered differently at the provider, a rejected code exchange (wrong secret, verifier or redirect URI), an invalid ID token, or an unverified or missing email. The server does not log which check failed, to keep codes, tokens and claims out of logs; reproduce with the provider's own logs. After a provider key rotation the JWKS is refreshed when a token names an unknown key; retry if a sign-in fails at that moment.

## Verification

- Unit (`tests/Penny.Backend.UnitTests/Authentication`, `Configuration/AuthOptionsTests`): Identity hash round trip and format, rejection of legacy/empty/malformed hashes, rehash detection, zod email/length parity (cases cross-checked against zod 4.6.7), token hashing, IPv6 grouping and configuration validation.
- Integration against real PostgreSQL 18 and Kestrel (`Controllers/AuthTests`, `Http/SecurityPolicyTests`, `Migrations/ImportedAuthTests`): register/login/me/logout over cookies and bearer tokens, stored token hashes, bearer precedence, per-session revocation and account isolation, exact millisecond expiry and expired-row purge, generic credential errors, upgrading weaker stored hashes on login, registration policy, concurrent registration (one 201, one 409, one user and ledger), rolled-back registration when the initial ledger fails, allowed and rejected origins and preflights, the 40-request window per host, proxy trust and liveness with the database down. The import test runs an imported SQLite account: its legacy scrypt hash is rejected with the generic error and left unchanged, imported sessions work until expiry, revoking one leaves other accounts' sessions, and expired-session purge cascades to push devices. It also checks that mixed-case legacy emails keep their legacy behavior.
- OIDC unit (`Configuration/OidcOptionsTests`): legacy defaults, optional/empty settings, required-setting, issuer and redirect URI validation, setting names in errors and secret redaction.
- OIDC integration against real PostgreSQL 18 and a deterministic local provider (`Infrastructure/FakeOidcProvider`: loopback Kestrel with a throwaway HTTPS certificate pinned by the API's provider client, per-run RSA signing keys, discovery/JWKS/token/UserInfo endpoints that check client, secret, redirect URI, single-use code and PKCE; no external network). `Controllers/OidcTests`: disabled routes, the authorization URL and stored hashed attempt, unconfigured redirects, first sign-in creating user/identity/ledger/session with cookie and bearer use, replay, changed provider email, registration disabled, email collision without linking, concurrent first sign-ins (one account), four concurrent redemptions of one attempt (one 200, one token request), exact expiry boundary and purge, unknown transactions, invalid bodies and oversized callbacks, wrong/missing/repeated state, redirect mismatches and fragments, cancellation, missing code, wrong or missing `iss`, bad nonce/audience/issuer/expiry/signature/subject, unverified or invalid email, UserInfo subject mismatch and fallback, provider unavailable or advertising another issuer, completion on a new host after a restart, the 1,000-attempt bound, rollback when the initial ledger fails, and startup failure on invalid settings. `Http/OidcPolicyTests`: one rate-limit window shared with password sign-in, and rejected origins that leave the attempt usable. `Migrations/ImportedOidcTests`: an imported SQLite identity signs in to its existing account with a changed email while registration is disabled, and a new subject cannot claim its email.

The legacy equivalents are `tests/core/server-boundaries.test.ts`, `tests/core/server.test.ts` and `tests/core/oidc.test.ts`.
