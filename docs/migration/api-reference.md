# Penny API compatibility reference

[OpenAPI 3.1](../../contracts/openapi.json) version 1.1.0 describes **40 implemented operations on 31 paths** plus one explicitly planned search v1 operation. It restores the October contract and corrects current `/api/info`, share-payment, lowercase response-envelope, optional move-target, membership and scheduled-projection drift. `x-implementation` distinguishes legacy/planned routes (later versions add `backend-foundation` and `backend`, below). Existing Node responses and `src/data/households.ts` are the compatibility baseline; only MAZ-121 implements the new search route.

## Transport, identity and errors

- Base path `/api`. Health/info, register/login and OIDC discovery/start/complete precede authentication. Candidate-server verification calls info with credentials omitted and redirects rejected; the current native client accepts `{name:"penny",version:<nonempty string>}`. Web uses its hosting origin.
- Web uses `penny_session`, a 64 lowercase hex token in an HttpOnly, SameSite=Lax `/api` cookie, max age 30 days; Secure follows deployment settings. Native uses `Authorization: Bearer <token>`. A syntactically valid bearer takes precedence over cookies (including expired bearers); malformed bearers fall back to a valid cookie as today. Storage holds SHA-256 token hashes; logout revokes one session and its devices.
- Preserve configured CORS with credentials, Origin checks on non-GET requests, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, 20MB JSON and 10MB decoded receipt limits. Preserve cookie/proxy/OIDC callback paths when deploying a separate web bundle and API.
- JSON errors are `{error:string}`. Branch on status, not English text: 400 invalid/unsafe legacy input, 401 session, 403 origin/permission, 404 absent/private, 409 revision/domain conflict, 413 size, 429 rate limit, generic 500. Cutover maintenance/search timeout uses additive 503 with Retry-After, never acknowledges a save. OIDC attempts remain expiring/single-use and server-side PKCE/nonce/issuer verification is retained.
- Existing clients send no capability/minimum-version signal. No new mandatory header or 426 is introduced. Keep unsafe pre-v3 writes guarded by current 400 behavior; negotiate future breaking changes explicitly before enforcing them.

## Values and revision units

IDs are opaque existing strings, not necessarily UUIDs. Calendar dates are real `YYYY-MM-DD` in 2000-01-01..2100-12-31, months `YYYY-MM`, timestamps integer Unix milliseconds. Money uses integer cents up to 99,999,999,999; shared percentages use integer basis points. Validate real dates/cross-field constraints in services as well as schema patterns. Preserve omitted optional fields versus null. C#/Swift serialization must not convert dates to zones or use floating-point currency.

`GET /ledger` returns `{revision,ledger}`; `PUT` sends the same whole-ledger unit and increments the matching revision once. 409 does not change data. Validate v1–v4 writes and normalize to v4; require v3 accounts/v4 trips and preserve pre-v3 account guards. Enforce entry kinds/category references, personal-share constraints, receipt ownership, household currency and linked-account deletion rules. Clients materialize personal recurrence and merge durable pending changes; the server does not.

Shared expense/rule edits/deletes carry entity revision. Creation begins at zero. Envelopes are lowercase `{household}`, `{expense}`, `{reimbursement}`, `{rule}`. `POST /households/{id}/expenses/{expenseId}/payments` accepts `{fromUserId,revision}` and returns 201 `{expense}` with `payments` and `paymentsClosed`; test stale/duplicate/settled shares. Optional `targetHouseholdId` moves expenses without changing identity under existing restrictions.

`GET /households/projection?month=YYYY-MM` or `year=YYYY` returns `{transactions,scheduled}`. Recorded entries use totalCents/shareCents; month-only previews carry scheduled/recurringId and never count as recorded spending. Shared rows remain separate from private ledger entries. Payer account references are omitted for other viewers; reimbursements record existing payments and never create spending. Former-member history follows server eligibility, not just presence of a cached row.

## Planned extension and drift gates

MAZ-51 adds the .NET foundation's public `GET /api/ready`, marked `backend-foundation` in OpenAPI 1.2.0: 200 `{ok:true}` when the restricted PostgreSQL runtime sees exactly the build's applied EF Core migrations and no pending import, otherwise sanitized 503 `{error:string}` with Retry-After. Liveness/info remain independent of database availability. The generated development document serves only implemented .NET controllers; no unfinished financial endpoints are advertised there. MAZ-53 adds the .NET `register`, `login`, `me` and `logout` operations with the contract operation IDs; they remain `legacy` in the shared contract while Node serves production. Imported legacy scrypt password hashes are not accepted, so those accounts must reset their password ([compatibility](authentication.md)). MAZ-55 adds the .NET `getApiLedger` and `putApiLedger` operations over the typed PostgreSQL ledger with the same envelope, v1–v4 validation/upgrade, messages, check order and 409 semantics; they also remain `legacy` in the contract. The few deliberate additions (trip-erasure guard for old clients, existing-household check, storable strings, last safe revision) and the wire/ordering rules are in [ledger sync](ledger.md). MAZ-54 adds the .NET `getApiAuthOidc`, `postApiAuthOidcStart` and `postApiAuthOidcComplete` operations with identical shapes, statuses and messages, also still `legacy` in the shared contract. Pending attempts move from process memory to PostgreSQL, so they survive restarts; the 10-minute lifetime, single use and the 1,000-attempt bound are unchanged ([OIDC](authentication.md#openid-connect-maz-54)).

MAZ-56 adds the .NET household membership operations with the contract operation IDs: `getApiHouseholds`, `postApiHouseholds`, `postApiHouseholdsTrips`, `getApiHouseholdsId`, `patchApiHouseholdsId`, `patchApiHouseholdsIdTrip`, `postApiHouseholdsIdInvites`, `postApiHouseholdsJoin`, `postApiHouseholdsIdLeave`, `deleteApiHouseholdsIdMembersUserid` and `postApiHouseholdsIdArchive`. They remain `legacy` in the shared contract. Shapes, statuses, messages and check order match Node; the deliberate differences are revoking invites on archive (an archived household's code is `400 Invite code is invalid or expired.`) and the storable-text rule. Rules, locking and differences: [households](households.md).

MAZ-57 adds the .NET shared-expense operations with the contract operation IDs: `getApiHouseholdsIdExpenses`, `postApiHouseholdsIdExpenses`, `getApiHouseholdsIdExpensesExpenseid`, `putApiHouseholdsIdExpensesExpenseid`, `deleteApiHouseholdsIdExpensesExpenseid`, `postApiHouseholdExpensePayment` and `getApiHouseholdsProjection`. They remain `legacy` in the shared contract. Envelopes, statuses, messages and check order match Node, with integer-cent equal/exact/percentage splits (golden cases in `contracts/fixtures/shared-splits.json`), date-based participants, payer-only account ids, per-expense revisions, soft deletes, moves, individual share payments and the read-only projection (recorded shares plus month previews of scheduled shares). The deliberate differences are a former member's projection (only their own shares instead of a legacy 404), ordinal percentage tie-breaks, audit snapshots without encrypted receipt filenames, id tie-breaks in ordering and the storable-text rule. Rules, locking, audit and differences: [shared expenses](shared-expenses.md).

MAZ-58 adds the .NET month recap, monthly reimbursement and audit operations with the contract operation IDs `getApiHouseholdsIdMonthsMonth`, `postApiHouseholdsIdMonthsMonthReimbursements` and `getApiHouseholdsIdAudit`. They remain `legacy` in the shared contract. Envelopes, statuses, messages and check order match Node: per-month integer-cent balances and full suggested transfers (golden cases in `contracts/fixtures/settlement.json`), the UTC month-end cutoff, separate overdue months, former-member visibility, household-locked reimbursement writes with audit/outbox rows, and newest-first audit history (500 household events, unlimited per expense). The deliberate differences are the former-member audit limit (filter, then limit), audit snapshots redacted on read (`accountId`, `receipt.name`) and id tie-breaks. Rules, locking and timing: [settlement](settlement.md).

MAZ-59 adds the .NET shared recurrence operations `getApiHouseholdsIdRecurring`, `postApiHouseholdsIdRecurring`, `putApiHouseholdsIdRecurringRuleid` and `deleteApiHouseholdsIdRecurringRuleid` (still `legacy` in the shared contract) with legacy envelopes, messages and check order, plus a PostgreSQL-leased occurrence runner. Create/update return the stored rule including `anchorDay` (an optional field the contract already allows). Deliberate differences: resuming a paused rule skips the paused dates, the runner increments the rule revision when it advances `nextDate`, anchors survive edits, equal rules store no allocations and failures are isolated per rule. Semantics, topology and recovery: [shared recurrence](shared-recurrence.md).

MAZ-60 adds the .NET receipt operations `postApiReceipts` and `getApiReceiptsId` (still `legacy` in the shared contract) over the encrypted file store. They keep the legacy JSON upload `{name,mime,base64}`, the 32-hex receipt ids and `/api/receipts/<id>` URLs, the messages, the 10 MiB decoded/14 MiB base64/20 MB request limits, the signature checks, the download headers (`inline; filename*=UTF-8''…`, `default-src 'none'; sandbox`) and owner-or-household access (current members, or former members with a share in a live linking expense). Deliberate differences: no ETag/304, storable filenames, and no request deadline on these two operations. Validation order, access, storage, backup and the `receipts-verify`/`receipts-sweep` commands: [receipts](receipts.md).

MAZ-61 adds the .NET push device operations `postApiPushDevices` and `deleteApiPushDevices` (still `legacy` in the shared contract) and a PostgreSQL-leased delivery worker. Contract **1.5.0** extends `PushDevice` with optional `provider` (`expo`, the default, or `apns`) and `environment` (`sandbox` or `production`, required for APNs) and admits hex APNs device tokens; legacy Expo bodies, the `201 {ok:true}`/`200 {ok:true}` responses and the `400 Invalid push device.` message are unchanged. Node ignores the new fields for Expo tokens and rejects APNs tokens with that 400, so native clients register only with .NET. Deliberate differences: messages expire after 24 hours, invalid-token cleanup spares a token registered again after the rejected send, and retries honor a longer `Retry-After`. Payloads, delivery semantics, Apple credentials and migration gates: [push](push.md).

MAZ-123 adds `POST /api/auth/password-reset` (`postApiAuthPasswordReset`) in OpenAPI **1.3.0**, marked `x-implementation: backend`: an operation that exists only in the .NET backend. Node never implemented it, so it is deliberately not `legacy` (the contract test requires `legacy` operations to equal the Node routes) and not `planned` (it is implemented). It is public (`security: []`), takes `{token, password}` (a 64-lowercase-hex operator-issued code and a 10–256-unit password, schema `PasswordReset`) and returns `200 {ok:true}` without issuing a session. Errors keep `{error:string}`: one generic `400 This reset code is invalid or has expired.` for every unusable code, `400 Enter a password of 10–256 characters.` (the code stays usable), `400 Invalid JSON.`, `403` origin, `413` and `429` from the shared sign-in limit. The request has no email, so it cannot reveal whether an account exists. Codes are issued only by the operator command `reset-password EMAIL`; see [password reset](authentication.md#password-reset-maz-123). Clients that predate it are unaffected.

Search v1 uses authenticated `POST /api/v1/search/transactions` over personal entries and visible shared expenses: accent- and case-insensitive substring, typo-tolerant and meaning-based (on-server embedding) matching, relevance or date/amount sorting over optional date ranges or all time, authorization before count/page, simple keyset cursors and explicit local pending/offline scope. [search.md](search.md) defines semantics, normalization and resource limits. MAZ-121 implements it in .NET only (contract 1.4.0 marks the operation `x-implementation: backend`; Node answers 404 and clients fall back to local search). Legacy clients keep working unchanged. PostgreSQL storage is internal; [mapping/cutover](postgresql.md) preserves wire values and revisions.

`tests/core/contracts.test.ts` checks exact implemented route coverage, unique operations/resolved refs, fixture schema subsets, v1–v4 upgrades, real HTTP/temporary SQLite cookie/ledger/409/shared-projection/share-payment behavior, substring fixtures and design trace coverage. UI tests consume the conflict fixture. This lightweight matcher is not a complete JSON Schema engine; Redocly validates the OpenAPI document separately. Service validation and real PostgreSQL cross-stack fixture consumption remain MAZ-52/62/64/121 gates. Do not report future PostgreSQL/Swift/browser behavior as verified by a schema or static storyboard.
